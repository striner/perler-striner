# 项目宪法

> 本文件不可修改！

## 项目定位

详见 [README.md HEAD](README.md)。

只要用户明确说明为“新需求”，所有开发都必须遵守本文规则。用户没有明确的，视为该工作是临时需求或非正式需求，可以跳过 SPEC 流程直接进入实现。

## SPEC 工作空间

每个正式新需求都必须在 [docs/spec/change/](change/) 下创建独立 SPEC 工作空间，目录命名格式为：

```text
${YYYY-MM-DD}_${name-split-with-hyphen}
```

示例：

```text
doc/spec/change/2026-07-10_add-tos-fallback-log/
```

该目录是需求讨论、规划、拆解和验收的唯一工作空间。所有文档使用中文书写

## 需求文档流程

每个正式需求必须在 SPEC 工作空间内，按顺序与用户讨论并形成以下文档：

1. `SPEC.md`
2. `PLAN.md`
3. `TASK.md`

### SPEC.md

`SPEC.md` 描述“为什么要做”和“做到什么”。它用于明确问题背景、目标、边界、用户可感知行为和验收标准，不应包含具体实现方案。后续读者应能通过该文档快速理解这个需求解决了什么问题。

### PLAN.md

`PLAN.md` 是技术规划，承接 `SPEC.md` 中的问题、目标和约束，指导后续任务执行。每项计划都应说明：

- 做什么
- 回应了 `SPEC.md` 中的哪条目标或约束
- 怎么实现（具体可实现的动作）
- 期望结果是什么

每项计划要详细，用户一目了然知道你要具体做些什么。

### TASK.md

`TASK.md` 是可执行任务清单，应按执行依赖关系排列。每个阶段对应 `PLAN.md` 中的工作项；同一阶段内相互独立的任务可以并行执行。

这个文档用户不会直接阅读、确认、干预，尽可能足够具体，精确到操作哪些文件、怎么操作，以便于执行、检查和复盘。

## 正式工作准入

正式实现前，必须先逐步构建并确认需求文档。默认流程是：

1. 根据用户需求先生成初版的 `SPEC.md`、`PLAN.md`、`TASK.md`。基于 `SPEC.md` 形成 `PLAN.md`，基于 `PLAN.md` 拆解 `TASK.md`。
2. 然后与用户澄清 `SPEC.md`，和用户反复沟通，直到用户确认可以进行下一步。期间对 `SPEC.md` 的修改视情况更新下游 `PLAN.md`、`TASK.md` 的对应部分。
3. 然后与用户反复确认 `PLAN.md` 内容。如需修改，要确认是否符合上游 `SPEC.md` 内容，如有不符合或者有歧义，必须要求用户先修改 `SPEC.md` 再返回来修改 `PLAN.md`。直到用户确认可以进行下一步。期间对 `PLAN.md` 的修改视情况更新下游 `TASK.md` 的对应部分。
4. 按 `TASK.md` 执行实现与验证

只要用户明确说明为“新需求”，必须经过完整 SPEC 流程。

遇到需求外的问题（如历史遗留问题），不要擅自修改，需要和用户确认是否加入本次需求。

## 历史需求与冲突检查

开始新需求时，应根据需求影响范围查阅已有 `docs/spec/change/*/SPEC.md`。需要及时向用户暴露以下问题：

- 需求冲突：新需求与已有行为、边界或验收标准不一致
- 需求重复：已有 SPEC 已覆盖相同目标
- 需求耦合：新需求依赖或影响其他需求、模块或约束

目标不是机械阻塞开发，而是帮助用户在全局视角下判断优先级、边界和演进方向。

## Skill 管理

需求工作期间沉淀出的新 skill，应放在 [docs/spec/skill/](skill/)

实现需求时可以使用这些 skill，但需要确保 skill 的用途、适用范围和限制清晰可追溯。

## 验证与验收

所有正式需求都必须包含“如何验证/验收”。验证方式应覆盖全周期，而不是只在最终交付时使用。理想情况下，验证项应能在需求讨论、设计、实现、测试和复盘阶段持续执行，用于随时确认修改方向和结果是否正确。

验证内容应尽量具体，例如：

- 可运行的命令或脚本
- 需要设置的环境变量或凭证
- 预期输出、日志或行为
- 不能自动验证时的人工验收步骤

任何无法执行的验证项都必须说明原因和剩余风险。

## 其他规范

### Commit 与 Pull Request 规范

提交信息使用 Conventional Commits，例如 `feat(tos): add fallback logging` 或 `fix(hook): preserve pickle redirect order`。提交时使用 `git commit -s` 添加 DCO 签名。Pull Request 应说明行为变化、列出已运行命令、标明因凭证或网络原因跳过的测试。
