## 背景

首轮 Tiny Model 使用 YOLO-World、MobileSAM、OpenAI CLIP 和多语言 CLIP，通过中英文 Prompt 猜测用户希望保留的主体。该实现同时存在检测框、自动 Mask 候选和 CLIP 区域排序多条语义路径，模型工件约 919 MiB，职责不清且用户无法直观看到模型识别了哪些实体。

本次修订用两阶段交互取代 Prompt 路线：上传图片后立即分析全部候选实体并显示检测框，用户明确勾选要保留的具体实例，再执行精细分割、主体构图、扁平插画风格化、限色和像素化。用户选择承担主观语义取舍，后端模型只负责对象识别、边界与视觉转换。

## 目标

`tiny_model@1.0.0` 的完整流程为：

```text
上传原图
→ Prompt-free 对象分析（类型、bbox、置信度）
→ 前端叠加检测框并让用户勾选具体实例
→ 选中 bbox 驱动高精度分割并合并 Mask
→ 透明边裁切、主体等比放大和居中
→ 轻量 Cartoonizer 扁平插画风格化
→ 结构轮廓增强、区域一致性限色
→ 分区可控像素化
→ 固定分辨率 RGBA 输出
```

Browser Native 和 CV Native 行为不变。Tiny Model 任一后端阶段失败时继续使用浏览器处理并显示 5 秒可关闭通知。

## 用户可感知行为

1. 用户选择 Tiny Model 后上传图片，或已有图片时切换到 Tiny Model，前端立即进入“分析中”并调用后端对象分析接口，不需要先点击 Generate。
2. 分析成功后，原图上叠加候选实体 bbox、编号和 YOLOE 原始英文类型。每个具体实例具有独立复选框；点击 bbox 或复选框都可以切换选择。
3. 默认只勾选显著性最高的候选实体。至少选择一个实体后 Generate 才可用。
4. 已选择的 bbox 使用明确的实线强调，未选择 bbox 使用弱化样式；同类型多个实例使用稳定编号，例如 `person 1`、`person 2`。
5. 用户点击 Generate 后，前端提交分析凭证和所选实例 ID。生成期间相关输入锁定并显示等待；成功后按钮变为 Download。
6. 修改实体选择、目标宽度、颜色上限或其他生成参数会使现有结果失效，但不重复对象分析；上传新图片会取消旧分析并重新开始。
7. 分析失败、无有效候选、凭证失效、精细分割失败、风格化失败、HTTP 错误或非法响应均进入既有浏览器回退，不向用户展示内部堆栈。
8. Tiny Model 不再显示或提交 Subject Prompt；对象名称直接使用 YOLOE 内置英文类别，不做翻译。

## 两阶段 API

### 对象分析

新增 `POST /api/v1/analyze`，使用 multipart 上传图片并声明 `tiny_model@1.0.0`。成功响应继续使用统一信封，并在 `data` 中返回：

- `version`：分析契约版本，首版为 `1`。
- `analysis_token`：带签名、短时有效的无状态分析凭证。
- `image.width` / `image.height`：后端完成方向归一化后的坐标空间。
- `objects`：最多 `24` 个候选实例。每项包含稳定 `id`、`type_id`、`type_name_en`、`confidence` 和归一化 `bbox`。

`bbox` 使用 `[0, 1]` 范围内的 `x`、`y`、`width`、`height`。响应不返回原图、Base64 图片或完整 Mask。

### 成品生成

现有 `POST /api/v1/process` 保持输出契约，在 Tiny Model 的 `algorithm_params` 中接收：

- `analysis_token`：对象分析返回的凭证。
- `selected_object_ids`：至少一个且不得重复的候选实例 ID。
- `max_colors`：默认 `16`，允许 `4–20` 的整数。
- 既有边缘和采样参数。

前端重新提交同一原图。后端校验凭证签名、有效期、算法版本和图片 SHA-256；校验失败视为算法错误并触发前端回退。凭证只包含图片摘要、模型版本、候选类型和 bbox，不包含图片像素。

所有响应信封保持 `code`、`msg`、`data`、`exec`、`meta.accept_id`、`meta.perf_time_use`。`code != 200` 时 `exec` 可包含 Exception Class。

## 模型路线

1. 对象分析首选 `yoloe-26m-seg-pf.pt`。它使用内置 4,585 类词表，一次输出类型、bbox、粗 Mask 和置信度；首阶段只向前端公开 bbox 元数据，粗 Mask 仅用于后端候选清理。
2. 类型名称直接使用 YOLOE 内置词表的原始英文标签。后端合并同一实体的重叠标签，过滤不能作为可选择实体的抽象标签，并限制候选数量；不加载或维护翻译标签表。
3. 用户选择后使用 `sam2.1_s.pt`，以所选 bbox 为提示分别生成精细 Mask。各实例独立修复后再做并集，不跨实例填充背景。
4. 风格化通过独立 `Cartoonizer` 接口实现。当前 POC 使用 AnimeGANv2 PyTorch `celeba_distill` 评估权重，以 768px 最长边执行单次生成；最终交付权重必须允许目标部署方式，并以参考图的扁平色块、低微纹理和清晰结构轮廓为固定风格。
5. 当前 YOLO-World、MobileSAM、OpenAI CLIP 和多语言 CLIP 路线被本修订取代，不再属于 Tiny Model 的运行时必需工件。

对象分析与精细分割模型约 157.5 MiB，当前 Cartoonizer 权重约 8.2 MiB，完整运行工件约 165.7 MiB，控制在 200 MiB 内。

### Cartoonizer POC 选型记录

- `celeba_distill`：三组候选中最接近目标参考图的扁平色块和低纹理风格，作为当前 POC 实现。
- `face_paint_512_v2`：对人物身份特征的保持相对更好，但整体仍偏绘画质感，不满足当前扁平化目标。
- `paprika`：色相和明暗迁移过强，与原图关键颜色及参考风格偏差较大，不采用。
- 权重插值试验未得到稳定的风格与身份保持折中，结果劣于直接使用候选权重，因此不进入运行链路。

## 图像处理边界

- 检测、分割必须使用未量化原图。
- 主体 Mask 形成后自动裁掉透明外边，全部选中实例使用联合包围盒等比放大并居中；不拉伸、不裁切主体。
- Cartoonizer 只改变主体 RGB 风格，不得移动、增加或删除实体；最终 Alpha 仍由精细 Mask 决定。
- 结构边缘融合原图长轮廓与风格化区域边界，过滤摄影噪声和短微纹理。
- 后端颜色量化与品牌无关，发生在风格化之后，只统计有效前景并保证不透明 RGB 唯一色数不超过 `max_colors`。
- 前端继续完成拼豆品牌色板匹配、抖动、统计、渲染和导出，并将最终品牌色数量限制在同一 `max_colors` 内。
- 固定分辨率输出仍为严格 `width * height * 4` 字节 RGBA。

## 运行与安全约束

- 模型文件不提交 Git，不在请求路径自动下载；通过显式预取命令下载到 `data/model/` 并校验大小和 SHA-256。
- 生产使用 NVIDIA CUDA + PyTorch；开发允许显式 FP32 CPU 调试，不承诺 CPU 性能。
- 单 GPU 默认推理并发为 `1`。分析和生成共享受控队列，不阻塞 ASGI 事件循环。
- 服务启动时加载并预热模型。真实 CUDA 热请求仍以 `3` 秒为目标，未实测前不得宣称达标。
- 不持久化用户原图、Base64、分析 Mask 或成品；不在日志记录 token、图片摘要或候选框。分析 token 默认短时有效且由服务端密钥签名。
- Ultralytics 运行时及 YOLOE 权重采用 AGPL-3.0；SAM2.1 采用 Apache-2.0。AnimeGANv2 PyTorch 架构代码采用 MIT，当前转换权重仅用于 POC 评估，生产使用前必须确认上游训练数据和权重授权。

## 当前 POC 验证记录

- 使用真实样本 `007-src.jpg` 完成对象分析，返回 10 个候选对象；API 和前端均直接显示 YOLOE 原始英文标签，前端实例标签包含 `person 1`。
- 在纯 CPU 后端环境完成 `/api/v1/analyze` 与 `/api/v1/process` 真实调用，并在 Chrome 桌面和移动视口完成上传、对象选择、Generate、等待、Download 及后端失败回退验证。
- AnimeGANv2 `celeba_distill` 已接入完整生成链路；集成结果保持由 SAM Mask 决定的 Alpha，并完成后续边缘增强、最多 20 色量化和固定分辨率 RGBA 输出。
- 相比未接入 Cartoonizer 的结果，当前 POC 的色块扁平度和摄影微纹理抑制已有明显改善，但仍未达到目标参考图的一致性；嘴部、眼镜及人物身份细节可能被改变。
- 上述记录只证明当前 POC 链路和单个参考样本可运行，不替代扩展样本风格验收、生产权重授权确认或目标 CUDA 设备性能验收。

## 验收标准

- 使用 `007-src.jpg` 等真实图片验证上传后自动分析、bbox 对齐、原始英文类型、实例勾选、默认主体和取消请求。
- 覆盖多人物、人物与台阶、动物、边缘主体、重叠对象、无候选和超过 24 个候选场景。
- 选择不同实例后生成结果只保留所选实体；同类型实例可以单独选择。
- 分析 token 被篡改、过期、对应不同图片或包含未知实例 ID 时必须拒绝。
- 生成结果背景透明、主体不拉伸不裁切，颜色数量和 RGBA 长度满足契约。
- 模型缺失、分析失败、生成失败和响应非法时前端回退与通知正确。
- 后端 Ruff/pytest、前端 Vitest/Astro check/build 通过；真实浏览器验证 Tiny Model 的分析、选择、Generate、等待与 Download 状态。

## 已确认事项

- Tiny Model 采用上传后自动分析、用户勾选具体实体、再次点击 Generate 的两阶段交互。
- 第一阶段返回 YOLOE 原始英文类型和 bbox，并叠加显示在原图上，不做类别翻译。
- 不再依赖中文或英文 Prompt，不再使用 CLIP 对图片区域做文本相似度匹配。
- 运行模型总体积允许位于约 50–200 MiB，优先质量与体积比。
- 首选 YOLOE-26M Prompt-free 做对象清单，SAM2.1-S 做所选 bbox 的精细分割。
- 后端始终移除背景；前端负责拼豆色板匹配、统计、渲染和导出。

## 待确认事项

1. 将 POC `celeba_distill` 替换或确认为最终 Cartoonizer 时，仍需确认上游训练数据、权重授权、固定参考风格，以及嘴部、眼镜和身份特征变化是否可接受。
2. 在扩展真实样本矩阵上确认 YOLOE-26M Prompt-free 原始类型、thing/stuff 候选覆盖率和 Cartoonizer 风格一致性。
3. 在目标 NVIDIA CUDA 设备确认显存、热请求时延和并发排队指标。

## 非目标

- 不改变 Browser Native 或 CV Native 的行为。
- 不实现关系、动作、排除条件等自然语言理解。
- 不在后端执行拼豆品牌色板匹配、统计、渲染或导出。
- 不为分析阶段返回完整 Mask 或持久化用户图片。
