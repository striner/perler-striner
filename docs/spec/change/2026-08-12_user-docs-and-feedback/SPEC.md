# 用户说明文档与反馈入口接入需求说明

## 1. 背景

当前系统是一个浏览器端拼豆图纸生成工具，用户可以上传图片、选择拼豆品牌、调整图纸参数、预览生成结果并下载 PNG 图纸。

随着系统功能逐步增加，用户需要更清晰地理解：

- 这个系统能做什么；
- 适合解决什么问题；
- 如何从零开始完成一次拼豆图纸生成；
- 每个操作项代表什么含义；
- 系统后续版本做过哪些更新。

同时，项目方希望收集用户在使用过程中的反馈和意见，用于发现问题、优化体验，并为后续接入客服能力预留入口。

## 2. 需求目标

### 2.1 用户说明文档入口

在系统右上角增加说明文档入口，让用户可以从主页面快速跳转到系统内置用户说明文档页面。

说明文档需要作为系统的一部分随代码一起维护和发布，并提供中英文双版本，帮助用户建立对系统的完整认知。文档需要提供足够清晰的新手友好操作指南，让不了解拼豆图纸生成流程的用户也能按步骤完成使用。

说明文档访问路径统一为：

```text
/perler-striner/pages/guide/zh/
/perler-striner/pages/guide/en/
```

### 2.2 用户说明文档内容

说明文档至少应覆盖以下内容：

1. 系统简介：说明系统是什么、适合谁使用、可以解决什么问题。
2. 使用前说明：说明图片处理在浏览器本地完成、图片不会上传服务器等基础信息。
3. 新手上手指南：按步骤说明如何上传图片、选择色卡、调整宽度、开关去背景/抖动/网格、查看配豆清单、下载图纸。
4. 参数解释：解释主要操作项的含义和建议用法。
5. 常见问题：解释用户可能遇到的问题，例如图片效果不理想、背景去除不准、图纸太大或太小、颜色不完全一致等。
6. 版本更新记录：说明后续每个版本的更新时间、操作人、版本、更新内容和主要变更。该记录可以人工维护或由 AI 总结，不要求展示提交链接。

每次打版本更新时，都必须同步把版本更新情况记录到用户说明文档末尾的版本更新记录中。该动作应与分支合并到 `master` 的操作挂钩：当需求分支或版本分支合并进入 `master` 前，应确认用户说明文档中的版本更新记录已补充对应条目。

### 2.3 用户反馈入口

在系统右下角增加一个悬浮反馈入口，让用户在使用过程中可以随时提交反馈或意见。

反馈入口需要明显但不打扰用户使用主流程。入口文案应让用户明确知道这是反馈渠道。

当前阶段先不实现复杂反馈表单、反馈数据存储、后台管理、自动邮件发送和数据库能力。这些能力等后续接入后端和数据库后再单独设计。

本次先提供一个简单反馈入口，让用户知道如果有问题或建议，可以通过问卷反馈。问卷链接为：

```text
https://v.wjx.cn/vm/wFChGhh.aspx
```

同时保留邮箱作为补充联系方式：

```text
striner@foxmail.com
```

反馈入口点击后跳转到外部问卷，由问卷平台负责收集和存储反馈。问卷反馈可以避免当前系统没有后端和数据库导致的反馈存储问题，是当前阶段可行的轻量方案。

### 2.4 后续客服扩展预留

本次需求需要为后续接入客服能力保留扩展空间。当前阶段不强制实现在线客服系统，但反馈入口的设计不应阻碍未来扩展为“反馈 + 客服”组合入口。

## 3. 范围

### 3.1 本次需求包含

- 在页面右上角接入说明文档入口。
- 将说明文档作为系统内置页面承载。
- 支持中英文双版本说明文档页面。
- 统一说明文档访问路径为 `/perler-striner/pages/guide/zh/` 和 `/perler-striner/pages/guide/en/`。
- 在站内说明文档中提供面向普通用户的新手上手指南。
- 在站内说明文档中加入版本更新记录区域。
- 规定每次版本更新时同步维护说明文档末尾的版本更新记录。
- 在页面右下角接入悬浮反馈入口。
- 本次反馈入口先做轻量实现，点击后跳转到问卷链接 `https://v.wjx.cn/vm/wFChGhh.aspx`。
- 在说明文档中保留 `striner@foxmail.com` 作为补充联系方式。
- 保持中英文页面现有能力不被破坏；中英文说明文档与反馈体验均需可用。

### 3.2 本次需求不包含

- 不实现完整用户账号体系。
- 不实现后台反馈管理系统。
- 不实现在线客服 IM 系统。
- 不实现数据库存储。
- 不要求把用户图片或生成图纸上传到本项目自建后端。
- 不实现系统内反馈数据存储。
- 不实现系统内反馈后台管理。
- 不实现网页内无感自动邮件发送。
- 不要求自动从 Git 历史生成版本更新记录；版本更新记录可以人工维护或由 AI 总结。
- 不要求在版本更新记录中展示 GitHub 提交链接。

## 4. 用户可感知行为

### 4.1 说明文档入口

用户打开系统后，应能在页面右上角看到说明文档入口。

点击该入口后，用户应能跳转到对应语言的系统内置说明文档，阅读系统介绍、操作教程、常见问题和版本更新记录。

### 4.2 说明文档阅读体验

用户阅读说明文档时，应能按步骤理解如何使用系统完成以下流程：

```text
打开系统
→ 上传图片
→ 选择拼豆品牌/色卡
→ 调整图纸宽度
→ 选择是否开启去背景、抖动、网格
→ 查看预览图纸
→ 查看配豆清单
→ 下载 PNG 图纸
```

### 4.3 反馈入口

用户打开系统后，应能在页面右下角看到悬浮反馈入口。

点击反馈入口后，用户应能获得一个简单明确的反馈渠道。

点击反馈入口后，用户应能跳转到外部问卷页面：

```text
https://v.wjx.cn/vm/wFChGhh.aspx
```

问卷平台负责反馈表单、提交确认、数据存储和结果查看。

反馈入口不应遮挡核心操作区的主要按钮，不应影响图片上传、参数调整、图纸预览和下载。

### 4.4 版本更新记录维护行为

每次打版本更新时，应在用户说明文档末尾的版本更新记录中新增一条记录。

该记录应至少包含：

- 更新时间；
- 操作人；
- 版本；
- 更新内容；
- 主要影响或用户可感知变化。

当分支准备合并到 `master` 时，应检查并确认该版本更新记录已经补充完成。

## 5. 验收标准

### 5.1 说明文档入口验收

- 页面右上角存在说明文档入口。
- 入口文案清晰，中文页面应能体现“说明文档”或等价含义。
- 点击入口后可以跳转到系统内置说明文档。
- 中文页面跳转到 `/perler-striner/pages/guide/zh/`。
- 英文页面跳转到 `/perler-striner/pages/guide/en/`。
- 说明文档入口在桌面端和移动端均可访问。

### 5.2 说明文档内容验收

- 说明文档包含系统简介。
- 说明文档包含新手上手指南。
- 说明文档包含主要参数解释。
- 说明文档包含常见问题。
- 说明文档包含版本更新记录区域。
- 说明文档同时具备中英文双版本。
- 版本更新记录至少具备以下字段表达：时间、操作人、版本、更新内容。
- 每次打版本更新时，应有对应的版本更新记录维护要求。

### 5.3 反馈入口验收

- 页面右下角存在悬浮反馈入口。
- 入口在桌面端和移动端均可见、可点击。
- 点击入口后可以进入轻量反馈渠道。
- 反馈入口应跳转到问卷链接 `https://v.wjx.cn/vm/wFChGhh.aspx`。
- 说明文档中应保留 `striner@foxmail.com` 作为补充联系方式。
- 反馈入口不阻断主流程操作。
- 反馈入口文案清晰，中文页面应能体现“反馈”或等价含义。

### 5.4 后续扩展验收

- 当前反馈入口实现方式应便于后续替换或扩展为客服入口。
- 后续如增加客服，不应要求大规模重写页面主体结构。

### 5.5 版本更新记录验收

- 用户说明文档末尾存在版本更新记录区域。
- 版本更新记录支持人工维护或 AI 总结。
- 版本记录不要求展示提交链接。
- 版本记录应能体现与分支合并 `master` 相关的版本更新动作。

## 6. 已确认决策

1. 说明文档作为系统内置页面承载。
2. 说明文档提供中英文双版本。
3. 说明文档访问路径统一为 `/perler-striner/pages/guide/zh/` 和 `/perler-striner/pages/guide/en/`。
4. 当前阶段暂不实现复杂反馈表单、反馈数据存储、后台管理和网页内无感自动邮件发送。
5. 当前阶段反馈入口采用问卷反馈。
6. 问卷链接为 `https://v.wjx.cn/vm/wFChGhh.aspx`。
7. 补充联系邮箱为 `striner@foxmail.com`。
8. 版本更新记录不需要提交链接，可以人工写版本说明或由 AI 总结。
9. 版本更新记录需要记录操作人。
10. 每次打版本更新时，都需要把版本更新情况记录到用户说明文档末尾的更新版本记录中，并与分支合并 `master` 的操作挂钩。
11. 右下角反馈入口采用圆角悬浮按钮样式。
